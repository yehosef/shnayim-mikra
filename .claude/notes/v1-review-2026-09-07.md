## 🚨 CRITICAL (1)

### Two open tabs silently clobber each other's progress (whole-map write, no storage event sync)
`src/composables/useProgress.js:14` · votes: reproduce✓, user-impact✓, requirements✓

progress is a module-level ref hydrated once at import and every persist writes the entire map; there is no window 'storage' listener anywhere in src/, so a tab never learns another tab wrote. Marking verses read in one tab, then marking anything (or just closing) another stale tab, overwrites and permanently discards the first tab's marks across the whole progress object, not just the parsha being viewed.

**Fix:** Add a window 'storage' listener for 'shnayim-progress' that merges the incoming map into progress.value (per-parsha/per-verse OR of the booleans), or re-read-and-merge immediately before each setItem.


## ⚠️ HIGH (10)

### 'aliyah' reading style: never-go-backwards pointer guard breaks traversal at every aliyah boundary
`src/components/FocusMode.vue:278` · votes: reproduce✓, user-impact✓, requirements✓

In readingStyle 'aliyah', nextUnread legitimately moves the pointer backwards at each pass boundary (hebrew1 pass for the whole block, then hebrew2, then targum). Both FocusMode.vue's followPointer and ParshaDisplay.vue's advanceSelection refuse to follow a backward pointer, so after the first hebrew1 pass of any aliyah the pointer is permanently abandoned: focus mode silently reverts to verse-order and eventually exits early, and list view gets stuck toggling the last phase forever. The chosen reading style is effectively discarded.

**Fix:** Make the guard style-aware: for readingStyle 'aliyah' follow the pointer unconditionally (or only refuse jumps outside the current aliyah block); keep the backward-refusal for style 'verse'.

### targumType 'rashi' silently falls back to Onkelos unless the unrelated 'Show Rashi' toggle is also on
`src/composables/useData.js:68` · votes: reproduce✓, user-impact✓, requirements✓

Rashi data is only fetched and attached to verses when settings.showRashi is true; settings.targumType is never consulted in the data-loading path and nothing watches it for a reload. showRashi defaults to false. ### Weekly parsha resolution is permanently bypassed once the URL hash is set
`src/App.vue:22` · votes: reproduce✓, user-impact✓, requirements✓

App.vue writes the resolved weekly route into window.location.hash on first load and short-circuits on any non-empty hash thereafter, never calling getWeeklyParsha again. A plain reload, reopened tab, or bookmark of the app's own URL pins the user to whatever week they first visited, forever. The same short-circuit means settings.location can never change the displayed parsha either.

**Fix:** Track whether the hash was auto-written vs user-chosen and re-resolve against the current week when it was auto-written and no longer matches; use history.replaceState so it doesn't create a durable history entry.

### displayMode 'aliyah': the reading pointer is computed over the whole parsha and never scoped to the displayed aliyah, breaking rendering, seed/advance logic, and readingStyle traversal
`src/composables/useReadingState.js:24` · votes: reproduce✓, user-impact✓, requirements✓

blocks/pointer in useReadingState.js (18-45) are built from ALL aliyot with no scope input, so whenever displayMode='aliyah' and the user views an aliyah other than the pointer's, the pointer falls outside the filtered displayVerses list. This single root cause cascades into three concrete symptoms: (1) ParshaDisplay.vue's isPointer/inCurrentAliyah checks never match, so no ▶ marker or in-current-aliyah highlight ever renders for the viewed aliyah (VerseView.vue:15, :7); (2) ParshaDisplay.vue's seedSelectionFromPointer (377-390) falls back to index 0/phase 1 because findIndex returns -1, causing the first Space press to unmark an already-read phase instead of advancing, and advanceSelection gets permanently stuck at the end of the aliyah; (3) readingStyle='aliyah' (whole-aliyah-twice-then-targum) silently degrades to plain per-verse 1→2→3 traversal in both list view (advanceSelection, ParshaDisplay.vue:268) and FocusMode (pointerPosition, FocusMode.vue:214-220), because both depend on the same unscoped pointer/findIndex mechanism. ### toHebrew() spells the Divine Name for verse/chapter 15 and 16 (yod-heh / yod-vav instead of tet-vav / tet-zayin)
`src/utils/hebrewUtils.js:41` · votes: reproduce✓, user-impact✓, requirements✗

## 📝 MEDIUM (17)

### Progress flush relies on beforeunload only, which does not fire on iOS/PWA termination
`src/composables/useProgress.js:25` · votes: reproduce✓, user-impact✓, requirements✓

Writes are debounced 300ms and restarted on every new mark; the only flush path besides the timer is a beforeunload listener, which mobile Safari and backgrounded/swiped-away PWAs do not reliably fire. A user who marks the last verses of an aliyah and immediately swipes the app away loses every mark since the last flush. Same code path as settings, so it is systematic.

**Fix:** Flush on 'pagehide' and document visibilitychange === 'hidden' in addition to beforeunload; factor the flush body into a shared helper used by progress and settings.

### Yom-Kippur-on-Shabbat years: week 4-10 Tishrei resolves to Bereshit, then jumps backwards to Vezot Haberachah
`src/composables/useParsha.js:60` · votes: reproduce✓, user-impact✓, requirements✗

When Rosh Hashana falls Thursday, both 10 and 17 Tishrei are chag Shabbatot the walk-forward loop skips, so for dates 4-10 Tishrei (outside the day<=10 vzot window) it returns Bereshit three weeks early; then on 11 Tishrei it flips backwards to Vezot Haberachah for eleven days before returning to Bereshit again. Affects roughly 3 of every 10 years (e.g. 5789, 5792, 5795).

**Fix:** Enter the Vezot Haberachah window as soon as no parsha Shabbat remains before Sukkot, rather than keying purely on `day > 10`.

### resolveWeek always targets a future Shabbat, so 'late'/'past' urgency states and the just-read parsha are unreachable on any fresh load
`src/components/ParshaDisplay.vue:163` · votes: reproduce✓, user-impact✓, requirements✗

resolveWeek always picks `hd.onOrAfter(SHABBAT)` (today or later), so from Sunday 00:00 the default view is already next week's parsha and the just-completed parsha is dropped nowhere in the UI. ParshaDisplay only feeds `shabbat` into useDailyGuide when the viewed parsha equals the resolved week's route, so urgency() can only ever return 'open' or 'due' for the shown parsha (whose Shabbat is always >= today) and null status for any other parsha the user navigates to manually. The documented lenient 'late' window (through the following Wednesday) and 'past' are unreachable, along with DailyGuide.vue's late/past labels and CSS, and the Vezot Haberachah/Hoshana Rabbah deadline override that depends on the 'late' branch being reachable at all.

**Fix:** Have resolveWeek (or a wrapper) also expose the previous week's route/shabbat, and keep it as the default/available view through the lenient deadline so useDailyGuide receives a real shabbat for it and 'late'/'past' can render; feed the Vezot deadline logic off the same fixed resolution.

### `week` is computed from a non-reactive `new Date()`, so an open session never rolls over to the new week
`src/components/ParshaDisplay.vue:163` · votes: reproduce✓, user-impact✓, requirements✗

`const week = computed(() => resolveWeek(new Date(), ...))` has no reactive time dependency and only re-evaluates when settings.location changes, unlike useDailyGuide's ticking `now` ref. A PWA/tab left open across Saturday midnight keeps last week's shabbat, so status and the daily guide desync from a fresh reload of the same page at the same instant — two different answers for the same moment, and the daily suggestion is computed for the new week against the old parsha/Shabbat.

**Fix:** Derive `week` from the same ticking `now` (expose it from useDailyGuide or lift a shared `now` ref) so it recomputes when the civil day rolls over.

### Keyboard handlers ignore modifier keys, hijacking browser/OS shortcuts and mutating progress
`src/components/ParshaDisplay.vue:314` · votes: reproduce✓, user-impact✓, requirements✓

Neither the list-view nor focus-mode keydown handler checks ctrlKey/metaKey/altKey/shiftKey before acting and calling preventDefault, so OS/browser shortcuts like Alt/Cmd+ArrowLeft (Back) are swallowed and moved into selection changes, and Ctrl/Shift/Cmd+Space or Enter reach toggleCurrentPhase/advanceStep and write progress.

**Fix:** Early-return at the top of both handlers when e.ctrlKey || e.metaKey || e.altKey (and for Space, e.shiftKey).

### Any click inside the focus-mode content area marks the current phase read, including reference text and text selection
`src/components/FocusMode.vue:65` · votes: reproduce✓, user-impact✓, requirements✗

### offlineReady is only ever set on the very first service-worker install, so Settings permanently reports 'caching in background'
`src/composables/useOffline.js:16` · votes: reproduce✓, user-impact✓, requirements✓

With registerType 'autoUpdate', onOfflineReady only fires from the workbox-window 'installed' event, which fires only on first install, not on later sessions where the SW is already installed and up to date. ### check-styles.mjs opacity checks are line-anchored and miss compound-declaration lines and filter:opacity()
`scripts/check-styles.mjs:36` · votes: reproduce✓, user-impact✗, requirements✓

The opacity regex only matches when 'opacity:' is the first token on its own line, so any line combining opacity with other properties (e.g. a one-line keyframe step) is invisible to the checker with no allow-opacity requirement, and there's no check at all for `filter: opacity(...)`.
